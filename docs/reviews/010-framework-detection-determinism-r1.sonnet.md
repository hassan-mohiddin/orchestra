## Adversarial Spec Review: LLD-010 — Pre-commit Framework Detection Determinism\n\n**Reviewer:** Sonnet 4.6 (independent judge, different model from Opus author)\n**Doc:** `docs/features/010-framework-detection-determinism.md` r1\n**Cross-ref:** LLD-008 r3, LLD-009 r1, BUG-006, `cli/install_hooks.py`, `cli/templates/precommit-yaml-patch.txt`\n\n---\n\n### FINDING 1 — HIGH: The load-bearing technical claim in the Glossary and Problem Statement defect #2 is REFUTED by pre-commit.com docs\n\n**Location:** Glossary `pass_filenames` entry (line 15), Problem Statement defect #2 (line 31), snippet comment block (lines 113-116), A1 acceptance item (line 40)\n\nThe Glossary states: `pass_filenames: true → framework passes commit-msg-file path; pass_filenames: false → no positional arg.`\n\nThis is the entire premise of defect #2 and of A1's decision to set `pass_filenames: true` on the `orchestra-commit-msg` hook.\n\nPre-commit.com documentation states (exact quote): **\"commit-msg hooks will be passed a single filename -- this file contains the current contents of the commit message to be validated.\"** This is an unconditional statement about the `commit-msg` stage — the msg-file path is always passed by the framework, independently of `pass_filenames`. The prior-judge flag noted this, and independent WebFetch here corroborates it: the `commit-msg` hook stage inherits git's native behavior of always injecting the msg-file as the first positional arg, and `pass_filenames` governs the appending of *matched files* list, not the msg-file arg that git itself provides to the hook invocation.\n\n**Consequence cascade if the claim is wrong:** The entire rationale for defect #2 evaporates. `pass_filenames: false` on a `commit-msg`-stage hook would still receive the msg-file path as `$1` (via git's own mechanism, not the framework's file-matching mechanism). The snippet's `pass_filenames: true` may be technically harmless (the file still gets passed), but the *explanatory comment* in the snippet (lines 113-116) would be factually wrong, teaching consumers incorrect mental models about the framework. The Glossary entry would be wrong. The Problem Statement's \"defect #2\" would be a non-defect used to justify LLD-010's existence.\n\n**Action required:** Verify the actual behavior of `pass_filenames: false` on a `commit-msg`-stage hook empirically (spin up a test repo, install a hook with `pass_filenames: false`, check whether `$1` is populated). If the pre-commit docs are correct and `$1` is ALWAYS the msg-file regardless of `pass_filenames`, then: (a) Glossary entry must be corrected, (b) defect #2 must be re-worded or removed, (c) snippet comment must be corrected, (d) the residual question is whether `pass_filenames: true` on a `commit-msg` hook does anything harmful (e.g., appends a second arg that is also the msg-file, making `$1` and `$2` both the same path — or does it append matched-files after the git-injected arg?). This is a non-trivial behavior difference that must be empirically confirmed before the LLD is approved.\n\n---\n\n### FINDING 2 — HIGH: fsync pseudocode opens a NEW read file descriptor — the write is not synced\n\n**Location:** Design section `install_via_framework_apply`, line 244\n\n```python\nos.fsync(open(tmp).fileno())\n```\n\n`open(tmp)` opens the file in read mode (default `'r'`), obtaining a brand-new file descriptor that is entirely separate from the write fd used by `tmp.write_text(...)` on line 243. The write buffer was flushed by `write_text`'s implicit close (Python's `Path.write_text` opens, writes, closes atomically in its own fd). However, the OS page-cache dirtied by that write is NOT necessarily synced just because you fsync a *different* fd pointing to the same inode. On Linux, `fsync(fd)` on a read-only fd for a regular file does flush all dirty pages for that inode — this is technically correct on Linux but is an obscure, implementation-dependent behavior. On some BSDs and macOS it may not flush dirty pages from a different fd's write. More critically: calling `open(tmp)` without a `with` statement leaks the file descriptor. The established durable-write pattern is:\n\n```python\nwith tmp.open('w', encoding='utf-8') as f:\n    f.write(yaml.safe_dump(...))\n    f.flush()\n    os.fsync(f.fileno())\nos.replace(tmp, cfg_path)\n```\n\nThe LLD pseudocode should be corrected to this canonical form. As written, it conflates \"we opened a read fd to the same path\" with \"we fsynced the write\". This is a correctness defect that will survive into implementation if the pseudocode is taken literally.\n\n---\n\n### FINDING 3 — HIGH: `_emit_tailored_snippet` stub `...` has no implementable semantics\n\n**Location:** Design section, lines 209-218\n\n```python\ndef _emit_tailored_snippet(user_cfg: dict) -> str:\n    base = FRAMEWORK_SNIPPET_PATH.read_text(encoding=\"utf-8\")\n    if _hook_types_cover_commit_msg(user_cfg):\n        # strip lines between marker comments\n        ...\n    return base\n```\n\nThe stub says \"strip lines between marker comments\" — but the template file (`precommit-framework-snippet.yaml` as shown in the Design's snippet section) contains NO parsable BEGIN/END markers. The template is a raw YAML comment block with no `# BEGIN_DIRECTIVE` / `# END_DIRECTIVE` fence. The implementor has no contract for: which lines to strip, what delimiter string signals the boundary, whether the stripping produces syntactically valid YAML, and whether the stripped output correctly omits the `default_install_hook_types` block vs the entire comment preamble.\n\nThis is a design gap, not an implementation detail. The LLD must either: (a) define the marker format explicitly (e.g., `# [BEGIN hook_types_directive]` / `# [END hook_types_directive]` in the template, with the snippet Design section updated to show these markers), or (b) define `_emit_tailored_snippet` as returning a programmatically constructed string (not a text-strip of the template), specifying what sections are omitted. As written, T3a and T3b have no implementable contract — the test would pass on any behavior that doesn't crash.\n\n---\n\n### FINDING 4 — MEDIUM: Edge case 2 and Edge case 11 contradict each other on partial-config handling, and Edge case 2's mitigation is underspecified\n\n**Location:** Edge Cases section, Edge case 2 (line 300) vs the `--apply` flow (lines 229-231)\n\nEdge case 2 describes: user has `repo: local` with `orchestra-lint` only (partial config).
